1. Summary for decision makers

Bank Statement Analyzer gives forensic accounting students and fraud investigators a professional tool for reading bank statements, reconciling them, spotting fraud patterns and producing workpapers. It is free, it is open source, and it can run on your university's own website.

What it does

Reads bank and credit card statements from any bank, checks every account against the statement's own balances, flags patterns such as structuring and a draining balance, checks files for signs of editing, and exports Excel workpapers.

Who it's for

Forensic accounting and fraud examination courses, student clinics working real cases under supervision, and investigators supporting fraud victims.

What it costs

Nothing. The software and its updates are free under the Apache License 2.0. Your only costs are a small web server and staff time, plus an independent security review if your policies require one.

How data is protected

In the recommended setup, statements are read inside each person's browser and are never sent to the university's server or anyone else. Case projects are encrypted with a password.

Recommendation

Start with Option 1, the browser version, for one course or clinic. The university's server holds no case data, which keeps the security review simple. Add Option 2 later only if users need features it provides.

What we ask of a pilot university

  • A faculty sponsor with a course or clinic that will use it for one term.
  • An IT contact to host the browser version and handle the university's usual security review.
  • Feedback at the end of the term on what worked and what's missing.

4. Option 1: Browser version

Your server hands out the app's files. Each person's browser runs the app and reads statements on their own computer.

The page carries a strict security policy: the browser may load from, and connect to, your server only. That applies to the code that reads statements too, so statements cannot be sent anywhere, even by a software bug or a tampered component. In testing, the complete app ran with every outside connection blocked, and a deliberate attempt to contact another website was refused by the browser.

With Docker

docker run -d --name bank-statement-analyzer -p 8080:8080 --read-only --tmpfs /tmp \
  --restart unless-stopped ghcr.io/jdaiken/bank-statement-analyzer-browser:<version>

Images are published with each release. To build the image yourself from the source code:

git clone https://github.com/jdaiken/parsing_tool.git && cd parsing_tool
docker build -f deploy/browser/Dockerfile -t bank-statement-analyzer-browser .

The container runs the nginx web server as an unprivileged user on a read-only filesystem, accepts only read requests (an upload attempt returns 403), and sends the security headers. Put it behind your HTTPS load balancer or reverse proxy. On a network that inspects HTTPS traffic, pass your organization's certificate to the build: docker build --secret id=ca_bundle,src=ca.pem ... (used during the build only, never stored in the image).

On an existing web server, without Docker

  1. Download bank-statement-analyzer-offline-<version>.zip from the project's GitHub Releases page, or build it with python tools/build_offline.py.
  2. Check the zip against its published .sha256 fingerprint, and the unzipped folder against the SHA256SUMS.txt file inside it.
  3. Copy the folder to a site served over HTTPS.
  4. Turn on the security headers with the included settings: .htaccess (Apache, needs mod_headers), web.config (IIS) or nginx.conf.example. They also set the right file types (for example, .wasm as application/wasm).
What users experience

The first visit loads about 85 MB from your server, which is then cached. Projects are saved encrypted in that browser; users should download projects they need to keep, because clearing browser data erases them. For scanned statements, users run the computer version.

5. Option 2: Server version

The full app, including reading scanned statements, runs on your server behind your university login. Use it only on a server your institution approves for case data.

What's included

Sign-in container

oauth2-proxy sends people to your identity provider (Microsoft Entra ID, Google Workspace, Okta or any OpenID Connect provider) and tells the app who signed in.

App container

On an internal network with no published port and no internet access, so it can only be reached through sign-in. Unprivileged, read-only, all Linux capabilities dropped. Case data lives in a dedicated volume.

Setup

  1. Register the app with your identity provider as an OpenID Connect web application, with the redirect address https://<your-host>/oauth2/callback. Limit who can sign in at the provider.
  2. Configure: copy deploy/server/.env.example to .env and fill in the issuer address, client ID, client secret, cookie secret, allowed email domains and public address.
  3. Start:
    docker compose -f deploy/server/docker-compose.yml --env-file deploy/server/.env up -d --build
  4. Put it behind HTTPS: point your reverse proxy at 127.0.0.1:4180. It must pass WebSocket connections through.
  5. Pin the sign-in image to an exact version (a digest) in docker-compose.yml.
  6. Protect the data: keep the case-data volume on an encrypted disk, include it in backups, and limit who can log in to the server.

How it keeps people's cases apart

Two settings, already in docker-compose.yml, turn on server mode. Set them only on an approved server:

  • BSA_APPROVED_SERVER=1 removes the "demonstration copy" warning.
  • BSA_USER_HEADER=X-Forwarded-Email names the sign-in information the app trusts. The app keeps a separate project folder for each person and refuses to run without sign-in. Never expose the app container directly: that information is trusted only because sign-in is the only way in.
Server administrators

In this option statements are on your server while they're analyzed, and projects are stored there (encrypted with their owners' passwords). People with administrative access to that server are inside the trust boundary.

6. How the analyzer protects data

ProtectionHow it works
Statements stay localOption 1 and the computer version read statements on the user's computer. The computer version only accepts connections from that computer and sends no usage statistics.
No outside connectionsThe browser version's security policy allows connections to its own server only. Fonts and chart code are built in, so no outside service is ever called.
Encrypted projectsStatements, their file names, notes and the case log are encrypted with AES-256-GCM, with a key derived from the project password using scrypt (an OWASP-recommended setting). Tampering is detected. Lost passwords can't be recovered.
Encrypted sharingProjects are shared as encrypted .bsacase files with their own password.
Evidence integrityEach statement's SHA-256 fingerprint, the app version, the analyst and the time are recorded in every workpaper. Every transaction names its source file, page and line. Original files are never changed.
Leaky redactionsText hidden under black boxes but still in the PDF is detected, hidden, and reported.
Labelled demo copiesA copy running on a server that isn't approved shows a red warning not to upload real statements.
Supply chainEvery software component is pinned to an exact version and verified by its fingerprint. Container base images and build automation are pinned to exact digests. Automated tests run on every change, and security updates are proposed weekly.

Not covered by the software: workpapers and exports are ordinary Excel, CSV and HTML files (not encrypted); a compromised computer or browser extension can see what's on screen; and a clean document check doesn't prove a statement is genuine.

Updates

New versions are published as releases on the project's GitHub page, each with the offline package, its fingerprint, and both container images. To update, pull the new image (or replace the folder) and restart; projects and case data carry over. Watch the repository's releases to be notified.

Support and security reports

Questions and feature requests: through the project's GitHub page or justiceforfraudvictimsproject.org. Security problems: report privately through Report a vulnerability on the repository's Security tab, not in a public issue.

9. IT checklist

Before go-live (Option 1)

  • Files match SHA256SUMS.txt (or the image was built from a tagged release).
  • Served over HTTPS on a university address.
  • curl -sI https://<host>/index.html shows Content-Security-Policy with connect-src 'self' blob: data:, plus X-Content-Type-Options, Referrer-Policy and Permissions-Policy.
  • curl -X POST https://<host>/index.html returns 403.
  • In the browser's developer tools (Network tab), loading the sample statements and downloading a workpaper shows requests to your host only.
  • Typing fetch("https://example.com") in the browser console is refused with a Content Security Policy error.
  • The header reads "Private: runs inside your browser" and there is no red demonstration warning.

Before go-live (Option 2)

  • Visiting the site without signing in redirects to your identity provider.
  • The app container has no published port; only the sign-in container is reachable, through HTTPS.
  • Two different people do not see each other's projects.
  • Reading the scanned demo statement works, and it reconciles.
  • The case-data volume is on an encrypted disk and in the backup schedule.
  • The sign-in image is pinned to a digest; .env is kept out of version control.

Ongoing

  • Someone is assigned to watch for new releases and apply them.
  • Access to the server (Option 2) is reviewed each term.
  • Incidents are reported and handled under your institution's process.
